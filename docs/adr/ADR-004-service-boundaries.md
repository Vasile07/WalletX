# ADR-004: Define WalletX service boundaries

- Status: Accepted
- Date: 2026-10-04

## Context

WalletX is a simulated digital wallet platform with separate user, wallet, transfer, and notification concerns. The system must support authentication, wallet balances, simulated deposits, transfer execution, and event-driven notifications while keeping the architecture easy to reason about.

Without a defined ownership model, a later implementation could duplicate wallet logic in both the Transfer and Wallet services, mix authorization checks across layers, or create unclear data ownership. The project is developed solo, so separate databases per service would add unnecessary local development and operational overhead for the initial version.

## Decision

We define the following ownership and interaction boundaries:

- The User Service owns user identity and JWT issuance.
- The Wallet Service owns wallet records and balance state.
- The Transfer Service owns transfer records and workflow orchestration.
- The Notification Service owns notifications and downstream user-facing updates.
- All services use one shared PostgreSQL database for the initial version, with logical ownership of domain tables assigned to their respective services.
- Spring Boot services use Spring Data JPA with Hibernate to persist their own domain data.
- Domain classes use Project Lombok selectively to reduce boilerplate; setters are not generated by default, preserving explicit domain state changes.
- The API Gateway is the sole public entry point for browser and mobile clients.
- Synchronous REST calls are used for request/response flows, while RabbitMQ/Kafka carries asynchronous events and work items.
- All initial wallets are limited to the RON currency and deposits are simulated only.

## Rationale

This keeps each service aligned to a single domain and makes data ownership explicit, while one shared PostgreSQL database keeps the solo-developed project simpler to run. Using a shared database does not mean services may freely write to each other's domain tables; cross-domain operations still use service APIs or events.

## Consequences

### Positive

- Clear service boundaries improve implementation consistency.
- Each service owns a single source of truth for its domain data.
- One database reduces local setup and operational complexity for the initial project.
- Transfer orchestration can be validated without embedding balance logic into the identity domain.
- Event-driven notifications remain decoupled from transfer logic.

### Negative

- Cross-service calls are required for some workflows.
- Services share a database deployment, so database-level changes and availability affect multiple services.
- Data consistency depends on proper validation and event handling.
- The implementation needs explicit ownership checks in each service.
- Separate databases may be introduced later if scaling or operational requirements justify the added complexity.

## Related constraints

- Initial supported currency is RON only.
- Simulated deposits are allowed; real payment integration is out of scope.
- The system should favor explicit service boundaries over shared business logic.
